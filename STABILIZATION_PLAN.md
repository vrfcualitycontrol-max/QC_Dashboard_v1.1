# План стабилизации QC_Dashboard_v1.1 (для надежного использования)

Этот документ предназначен для агента-исполнителя. Он написан максимально пошагово: что делать, в каком порядке, где править файлы, какими командами проверять, и какой результат считать “готово”.

## 0) Контекст (что сейчас есть)

Репозиторий: `QC_Dashboard_v1.1`

Текущая архитектура (as-is):
- Frontend: статические `*.html` + `assets/js/*`, `assets/css/*`, графики через Chart.js CDN.
- Backend: FastAPI в `backend/app.py` (минимальные эндпоинты, часть заглушки).
- DB: Postgres через docker-compose.
- Data pipeline: `auto_updater.py` парсит `reports/*.xlsx` и `reports/*.pdf`, обновляет `assets/js/data.js` и записывает агрегаты в Postgres.
- Infra: `docker-compose.yml` + `nginx.conf` (nginx раздает статику и проксирует `/api`).

Ключевая проблема “стабильного использования” сейчас:
- `docker-compose.yml` содержит хардкодный Windows путь в `nginx.volumes` (непортируемо).
- Есть 2 источника данных одновременно: статический `assets/js/data.js` и попытка писать в Postgres/слать файлы в backend; нет единого “источника истины”.
- Backend пока не реализует ingest/upload API, которое вызывает `auto_updater.py` (`/api/upload/xlsx|pdf`).
- В репозитории лежат отчеты (`reports/`) и PDF-документы (возможно чувствительные).

## 1) Цели стабилизации (Definition of Done)

Считаем проект “в полном порядке” только если выполнено ВСЕ:
- Проект запускается одинаково на Windows/Linux/Mac одной командой `docker compose up -d --build` без ручных правок путей.
- Все секреты вынесены из репозитория (пароли/токены/ключи) и задаются через `.env`/секреты CI.
- Есть один четкий режим данных:
  - либо “Static Mode” (данные живут в `assets/js/data.js` и обновляются скриптом),
  - либо “API Mode” (данные живут в Postgres и фронт берет их из backend API).
  - Запрещено держать “и так, и так” без явного флага режима и документации.
- CI проходит полностью (workflow quality-and-security).
- Есть понятный Runbook: как обновлять данные, как бэкапить/восстанавливать, как диагностировать проблемы.

## 2) Правила безопасности (обязательные)

### 2.1 Немедленные действия (если еще не сделано)
- Если в чате/где-либо публиковался GitHub PAT токен:
  - Срочно отозвать (revoke) токен в GitHub Settings → Developer settings → Personal access tokens.
  - Создать новый с минимальными правами (обычно “repo:read” достаточно; для пуша — “repo”).
  - Проверить, не попадал ли токен в коммиты/файлы. Если попадал — удалить из истории (см. 2.3).

### 2.2 Запреты
- Нельзя хранить реальные пароли/токены в:
  - `docker-compose.yml`,
  - `docker-config.json`,
  - `assets/js/*`,
  - `README.md`,
  - любом `.md`.
- Нельзя добавлять в репозиторий реальные отчеты/персональные данные. Только демо-набор или пустая папка.

### 2.3 Проверка утечек в репозитории
1) Запустить локальный поиск по репозиторию на ключевые слова:
   - `ghp_`, `password`, `secret`, `token`, `POSTGRES_PASSWORD`, `DATABASE_URL`.
2) Если найдено в tracked-файлах — удалить/заменить на переменные окружения и обязательно ротировать секреты.
3) Если секрет попал в git-историю:
   - использовать `git filter-repo` (предпочтительно) или BFG,
   - после переписывания истории: принудительный push, уведомить всех пользователей, что нужно заново клонировать.

## 3) Фаза A — “Сделать запуск переносимым”

Цель: `docker compose up -d --build` работает без редактирования на любой машине.

### A1. Привести docker-compose.yml к переносимому виду

Файл: `docker-compose.yml`

Проблема: `nginx` монтирует хост-путь `D:/...` (Windows) в контейнер.

Сделать один из 2 вариантов (Рекомендуемый: Вариант 1).

#### Вариант 1 (рекомендуется): собирать фронтенд-образ из корневого Dockerfile
1) В `docker-compose.yml` для `nginx` заменить volumes на:
   - конфиг nginx (`./nginx.conf`)
   - убрать bind-mount фронтенда целиком (чтобы образ был самодостаточный)
2) Для `nginx` добавить `build: { context: ., dockerfile: Dockerfile }` вместо `image: nginx:stable`.
3) Убедиться, что корневой `Dockerfile` копирует `*.html` и `assets/` (он уже это делает).
4) Плюсы:
   - одинаково везде, нет зависимостей от путей на хосте,
   - “production-friendly”.
5) Минусы:
   - при разработке UI нужно пересобирать образ, чтобы изменения попали внутрь (можно оставить отдельный dev-профиль).

#### Вариант 2 (dev-режим): bind-mount текущей папки проекта
1) В `docker-compose.yml` для `nginx` заменить `source: "D:/..."` на `source: .`
2) `target` оставить `/usr/share/nginx/html`
3) Плюсы: изменения HTML/JS мгновенно видны без ребилда.
4) Минусы: больше “dev”-подход, хуже для прод.

### A2. Вынести конфигурацию в .env
1) Создать файл `.env.example` в корне репозитория со значениями-заглушками:
   - `POSTGRES_USER=qc_user`
   - `POSTGRES_PASSWORD=change_me`
   - `POSTGRES_DB=qc_dashboard`
   - `DATABASE_URL=postgresql+psycopg2://...`
   - `REPORTS_SOURCE=./reports`
2) Добавить `.env` в `.gitignore` (если еще нет).
3) Обновить `docker-compose.yml`, чтобы он читал переменные:
   - `POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}`
   - `DATABASE_URL: ${DATABASE_URL}`
4) В README добавить блок “Сначала скопируй `.env.example` → `.env`”.

### A3. Обновить volumes Postgres
Сейчас `postgres_data` помечен как `external: true`.

Решение (выбрать одно):
- Простое (рекомендуется): сделать volume не-external, чтобы проект поднимался “с нуля” у любого пользователя.
- Прод-решение: оставить external, но в README/Runbook написать команду создания volume и имя.

Критерий готовности фазы A:
- `docker compose config` проходит без ошибок.
- `docker compose up -d --build` поднимает 3 контейнера (postgres/backend/nginx).
- `http://localhost/index.html` открывается (редирект на analytics).
- `http://localhost:8000/api/health` отвечает 200/503 (в зависимости от DB), но не 404.

## 4) Фаза B — “Упорядочить данные и обновление”

Цель: один “источник истины”, понятный режим обновления, воспроизводимые скрипты.

### B0. Принять решение: режим данных
Агент должен получить от владельца проекта ответ:
- Режим 1: **Static Mode** (данные в `assets/js/data.js`, фронт не ходит за метриками в API).
- Режим 2: **API Mode** (данные в Postgres, фронт получает метрики через backend API).

Если ответа нет — временно делаем Static Mode (минимальный риск) и параллельно готовим API Mode как опцию.

### B1. Static Mode (если выбран)
1) `reports/`:
   - оставить папку пустой в репозитории (`.gitkeep`),
   - реальные отчеты хранить вне git.
2) `auto_updater.py`:
   - оставить обновление `assets/js/data.js`,
   - выключить все сетевые вызовы на backend (чтобы не было “псевдо-интеграции”), либо сделать это опциональным флагом:
     - env `ENABLE_BACKEND_SYNC=0/1`.
3) Документация:
   - описать “как обновить данные”: куда положить файлы, какую команду запустить, какой файл изменится.

### B2. API Mode (если выбран)
Цель: `assets/js/data.js` превращается в “пустой демо”, а реальные данные читаются из API.

Нужно сделать:
1) Backend: реализовать реальные endpoints:
   - `GET /api/employees` — список сотрудников (из DB).
   - `GET /api/history/{employee_name}` — история по периодам.
   - `GET /api/trends/forecast` — либо прогноз на бэкенде, либо отдача сырья для фронта.
2) Backend: реализовать ingest:
   - `POST /api/upload/xlsx` — принять файл, распарсить, записать в DB.
   - `POST /api/upload/pdf` — принять файл, распарсить, записать tendencies/rec в DB.
   - Минимально: сохранить файл в `/app/reports`, вызвать логику парсера.
3) `auto_updater.py`:
   - в API Mode он НЕ должен менять `assets/js/data.js`.
   - он должен либо:
     - только отправлять файлы в backend, либо
     - вообще не использоваться (обновление через backend endpoints).
4) Frontend:
   - добавить режим загрузки данных из API (например, `window.DASHBOARD_DATA` берется из `fetch('/api/metrics')`).
   - тактические страницы НЕ трогать: для них запрещено вводить зависимость от `fetch()` (требование стабильности из handoff).

### B3. Сделать генерацию tactical-data.js воспроизводимой
Сейчас markdown лежит в `content/`, а `assets/js/tactical-data.js` — результат.

Сделать:
1) Добавить скрипт `scripts/build_tactical_data.py`:
   - читает markdown из `content/` (конкретные файлы перечислить),
   - экранирует корректно строки,
   - генерирует `assets/js/tactical-data.js`.
2) Добавить команду в README:
   - “как обновить тактический контент”.
3) Добавить проверку в CI:
   - скрипт генерации запускается и сравнивает, что `assets/js/tactical-data.js` актуален (либо просто lint/синтаксис).

Критерий готовности фазы B:
- Выбран и задокументирован режим данных (Static/API).
- В README/Runbook есть 1 ясный путь “как обновить данные”.
- Нет “лишних” полуработающих интеграций (например, auto_updater вызывает API, которого нет).

## 5) Фаза C — “Стабилизировать backend (минимально, но правильно)”

Цель: backend не заглушка, а полезный сервис, либо честно остается “health only”.

### C1. Минимальный production-ready backend

Сделать:
1) Добавить конфигурацию через Pydantic settings или через env (минимум):

2) Добавить понятные ошибки:
   - если DB недоступна — health 503 и `database=error` уже есть; сохранить.
3) Реализовать хотя бы один полезный endpoint:
   - `GET /api/metrics` (или похожий) который отдает структуру, совместимую с `DASHBOARD_DATA`.
4) Добавить ограничения:

### C2. Тесты backend
Файл: `tests/test_backend_smoke.py`

Сделать:
1) Тесты не должны требовать реальный Postgres (использовать `DATABASE_URL=""` и проверять “not_configured”).

3) Если делаем API Mode — добавить тесты на новые endpoints, но так, чтобы можно было запускать в CI без внешних сервисов.

Примечание по зависимостям:

Критерий готовности фазы C:

- `pytest -q tests/test_backend_smoke.py` проходит.

## 9) План реализации по шагам (очень конкретно)

Ниже “скрипт для агента”, выполняй по порядку. Не перескакивай.

### Шаг 1 — Подготовка
1) Клонировать репозиторий.
2) Создать `.env` из `.env.example`.
3) Запустить:
   - `docker compose config`
   - `docker compose up -d --build`

Ожидаемый результат:
- контейнеры поднялись,
- `curl http://localhost:8000/api/health` возвращает JSON.

### Шаг 2 — Привести docker-compose к переносимости (Фаза A)
1) Исправить `docker-compose.yml` (см. A1).
2) Вынести креды в `.env` (см. A2).
3) Повторить запуск и проверки.

### Шаг 3 — Решение по данным (Фаза B0)
1) Получить ответ от владельца: Static Mode или API Mode.
2) Зафиксировать решение в README и CURRENT_STATE.md.

### Шаг 4 — Реализация выбранного режима (Фаза B1 или B2)
- Если Static Mode:
  - сделать `reports/` пустым в git,
  - сделать `auto_updater.py` без обязательных обращений к backend.
- Если API Mode:
  - реализовать ingest endpoints в backend,
  - реализовать чтение данных фронтом из API (не трогая тактические страницы).

### Шаг 5 — Тактический контент (Фаза B3)
1) Сделать генератор `assets/js/tactical-data.js` из `content/`.
2) Проверить `law.html`, `instruments.html`, `manual.html`.

### Шаг 6 — Тесты и CI (Фазы C/F)
1) Запустить локально:
   - `python -m compileall backend/app.py auto_updater.py`
   - `pytest -q tests/test_backend_smoke.py`
2) Убедиться, что CI проходит после пуша.

### Шаг 7 — Чистка (Фаза D)
1) Удалить `__pycache__` и прочий мусор.
2) Перепроверить, что ничего не сломалось (повторить шаг 6).

### Шаг 8 — Runbook (Фаза E)
1) Создать `RUNBOOK.md`.
2) Проверить, что инструкция работает на “чистой” машине/контейнере.

## 11) Примечания для агента (чтобы не сломать рабочее)

- Тактические страницы не должны зависеть от сетевых запросов во время рендера (требование стабильности): контент должен оставаться внутри `assets/js/tactical-data.js`.
- Не меняй порядок подключаемых скриптов на тактических страницах без необходимости (см. `AGENT_HANDOFF_v1.3.1.md`).
- Не коммить реальные отчеты/данные сотрудников. Для демо — обезличенный синтетический набор.
