# Бриф для чата «Протатип SaaS Аналитического Дашборда»

## 1) Контекст
- Есть основной проект: **«reference Dashboard_SC»** (веб/админка, источник данных и контента).
- Цель: сделать **современный мобильный SaaS** для отдела Soft Collection (ранняя стадия), полезный **ТимЛидам** и **Операторам**.
- Требование: основной проект и мобильный SaaS должны быть **максимально синхронизированы** (единый источник данных/контента).

## 2) Что переносим из «reference Dashboard_SC» в мобильный SaaS (включаем в MVP мобильного)
### 2.1 Аналитика качества (основа продукта)
Нужные экраны:
- **Главная сводка** (пульс команды/группы, зоны риска, кто просел/вырос).
- **Heatmap / диагностика** (провалы 0 / 0.5 / 1.0 по критериям + интерпретация).
- **Динамика** (недели внутри месяца + сравнение трендов).
- **Карточка сотрудника** (история, проблемные зоны, контекст успеваемости).

Метрики, которые обязательны:
- **TQS / качество** (итог + динамика).
- **AHT / время** (динамика).
- **Провалы по критериям** (кол-во/доля 0 и 0.5, критические просадки).

Разрезы времени:
- **Месяц + недели внутри месяца** (недели типа 01–08, 09–15 и т.д.).

### 2.2 Рейтинги
- Рейтинг нужен в мобильном.
- **Логика рейтинга: “по критическим”** (приоритет комплаенса/критических провалов; детали формулы уточнить).

### 2.3 База знаний (вся важна в мобильном)
Вынести в мобильное:
- **Возражения** (B2C/B2B).
- **Тактические инструменты** (argumentation / demand-setting / manipulation / closing-summary и т.п.).
- **Мануал/процесс** (manual-flow, обучение, темы).
- **Регламенты/CRM/SVP** (QC regulations, правила CRM, SVP/механики/методология).

Как показывать БЗ в мобильном:
- Приоритетный UX: **Избранное** (закладки) + “недавно просмотренные” (по умолчанию).

## 3) Что НЕ показываем в мобильном интерфейсе (оставляем “под капотом” / в админке)
- DevOps/CI/Docker/инфраструктура.
- Документация разработки (MVP/CHANGELOG/Release notes/архивы).
- Сырые файлы отчётов (PDF/XLSX) как файлы — в мобильном только агрегаты/выжимка.
- Скрипты обновления данных (auto_updater и т.п.) — скрыто.

## 4) Пользователи, роли и доступ
### 4.1 Регистрация в SaaS обязательна
Нужны **2 типа регистрации**:
- **ТимЛид SC**
- **Оператор SC**

### 4.2 Права ТимЛида
- Просмотр **командных показателей** (по своей группе).
- Просмотр **персональных показателей любого оператора** в группе (в контексте проблем/успеваемости).

### 4.3 Права Оператора
- Просмотр **своих персональных показателей**.
- Дополнительно: просмотр показателей **3 операторов выше него в рейтинге** (мотивационный режим).

## 5) Синхронизация и обновление данных (как хотим)
- Обновление данных идёт через **основной проект (reference Dashboard_SC) как “админку”**.
- Далее **мобильный SaaS транслирует данные из админки**.
- Источники обновления: **загрузка XLSX/PDF** (как в текущем подходе).

Требование к архитектуре синхронизации (в терминах продукта):
- Админка = место загрузки/парсинга/нормализации данных и контента.
- SaaS (мобилка) = клиент, который читает агрегированные данные/контент из админки через API.

## 6) Уведомления
- **Не нужны** (без пушей/алертов на старте).

## 7) Главные сценарии для мобильного SaaS
- Мониторинг KPI (кто просел/вырос, где риск).
- Коучинг/план действий (разбор проблемных зон, что улучшать).
- Тактические подсказки (быстро открыть во время работы).
- Контроль регламентов (быстро проверить “как правильно”).
